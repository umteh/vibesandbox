## Problem Statement

There is no good place for people who build AI-powered web and mobile apps to sell them. Existing directories (Product Hunt, There's An AI For That, Futurepedia) are SEO dumps with no quality gate. AppSumo and Gumroad aren't built for AI apps. What's missing: a focused marketplace where AI builders can list apps with prices, AI scores them by quality and taste, and buyers contact sellers directly — no platform payment processing, no friction.

## What Makes This Cool

An AI curation engine that judges apps by taste, not just "does it work." Every listing has a publicly visible quality score with reasoning — builders submit to learn from the critique, not just to get listed. The scoring engine IS the product. Everything else is packaging.

## Constraints

- Side project — should ship V1 in a weekend
- No payment processing (Craigslist model: platform facilitates contact, deal happens offline)
- Web platform, desktop-first (audience is builders on laptops)
- Builder = buyer: same community on both sides

## Premises

1. AI can evaluate "app quality" meaningfully — not just "does it work" but "is this good"
2. The primary audience (AI builders) are both buyers and sellers — one community, not two
3. The wedge is curation, not payments — prove the taste engine first
4. Web platform, not mobile-first
5. V1 is buildable in a weekend

## Approaches Considered

### Approach A: Minimal Taste Engine (original)
Submit URL → AI scores it → public feed. No auth. No payments. Weekend build.

### Approach B: Curated Directory + Payments
Creator accounts, Stripe, full marketplace. 1-month scope.

### Approach C: Taste Engine API / Widget
Just the scoring API, embeddable. Ultra-fast, viral distribution.

### Approach D: Craigslist-Style Directory (CHOSEN)
Creator accounts, submit app with desired price, AI quality score on every listing, encrypted email relay for buyer-seller contact. No built-in payments. Platform facilitates introductions.

## Recommended Approach — Craigslist-Style AI Marketplace

**Core flows:**

**Creator flow:**
1. Sign up (email + password, or GitHub OAuth)
2. Submit listing: app name, URL, description, category, screenshots, desired price (fixed or "make offer")
3. AI evaluates the submitted URL: takes screenshot, scores across 5-7 dimensions (UX clarity, problem sharpness, novelty, polish, usefulness), returns score 0-100 + 1-paragraph critique
4. Listing goes live with AI score badge and reasoning visible

**Buyer flow:**
1. Browse feed (sorted by AI score by default, can filter by category/price)
2. Click a listing → see full details, screenshots, AI critique, price
3. "Contact Seller" → modal form with buyer name, email, and message. Unauthenticated buyers allowed (no login required to contact). Platform generates a one-time relay token and forwards the message to the creator's real email via Resend/Postmark. The forwarded email includes: buyer's message, buyer's email address (so the seller can reply directly), and the asking price as set in the listing. Footer explains the relay mechanism: "This inquiry was forwarded by [platform name]. The buyer included their email above — reply directly to connect." Neither party is tracked after the initial relay.

**Listing states:**
- **Pending score**: Listing is created and visible in the feed with a "Scoring..." badge. Score is in-flight (Playwright screenshot + GPT-4o evaluation, typically <5 minutes).
- **Live**: Score badge shows 0-100, per-dimension breakdown, and 1-paragraph critique. Buyers can contact.
- Listings are never hidden in pending state — builders share "pending" URLs to show they submitted.

**Tech stack (weekend-feasible):**
- Next.js 14 (App Router) on Vercel
- Supabase (Postgres for listings + auth, storage for screenshots)
- Playwright on a Fly.io worker (headless eval of submitted URLs)
- GPT-4o with vision for scoring
- Encrypted email relay: UUID-keyed relay table. Buyer submits contact form with their email + message. Platform forwards once to creator's email (via Resend/Postmark). Creator email stored encrypted at rest (app-level AES-256 before insert, key stored in env var). Relay record expires_at = created_at + 24 hours. Relay job: decrypt creator email in-memory → send via Resend → mark forwarded_at. Buyer's email is sent in plaintext in the forwarded message body so the seller can reply directly off-platform. Relay records are deleted after 24 hours by a Supabase scheduled function (or Vercel cron).
- Tailwind + shadcn/ui for UI

**Database schema (core tables):**
```sql
listings (id, user_id, title, url, description, category, price_cents, price_type[fixed|offer|free], screenshot_url, screenshot_status[pending|captured|failed|auth_required], score, score_breakdown_json, critique, score_version, last_rescored_at, status[pending|scored|rejected], created_at, updated_at)
users (id, email_encrypted, github_id, created_at)
relay_tokens (id, listing_id, buyer_email_hash, token_uuid, buyer_email_encrypted, buyer_message, forwarded_at, expires_at)
-- buyer_email_hash: SHA-256 of buyer email + listing_id, used for idempotency check (one contact per buyer per listing)
-- Idempotency rule: if relay_tokens row with same listing_id + buyer_email_hash already has forwarded_at set, return 200 "Your message was already sent." Do not create a new row.
submission_log (id, user_id, listing_id, created_at)  -- for rate-limit tracking
```

**Eval worker communication pattern (A — fire-and-forget HTTP):**
- Submission API (Next.js/Vercel): creates listing with `status: pending`, fires background HTTP POST to `https://scorer.fly.dev/score` (no await), returns 201 immediately.
- Fly.io scorer worker: receives the job, runs Playwright screenshot + GPT-4o, calls back via `PATCH /api/listings/{id}/score`. Auth: HMAC-SHA256 signature of `listing_id + score_json + unix_timestamp` using `SCORER_HMAC_SECRET` env var. Vercel validates signature and rejects requests with timestamps older than 5 minutes (replay protection). Updates `score`, `score_breakdown_json`, `critique`, `status: scored`, `score_version: 1`.
- UI uses Supabase Realtime to subscribe to listing updates — score badge updates automatically when the row changes.
- If the Fly.io worker is down: listing stays pending, score never arrives. Acceptable for V1. Manual re-score via admin panel is the recovery path.

**Email encryption key constraint:**
- `EMAIL_ENCRYPTION_KEY` env var must NEVER be rotated in V1. Treat it like a database root password. If compromised: wipe all relay_tokens, notify creators to resubmit (V2 feature). Rotation without a migration makes all stored creator emails permanently unreadable — relay forwarding silently fails.

**Screenshot handling:**
- Playwright timeout: 10 seconds. On timeout, score with `screenshot_unavailable: true`.
- GPT-4o prompt falls back to description-only scoring when no screenshot available.
- If URL requires auth (login screen detected by presence of a password input), mark `screenshot_status: auth_required` and allow creator to upload a screenshot manually via the listing edit form.
- Screenshots stored in Supabase storage. No expiry — kept for the life of the listing.
- Score can be re-run manually (founder-only action via admin panel) if screenshot failed.

**The rubric (most important deliverable — define this before writing a line of code):**
Evaluate 20 AI apps manually. Write down what separates a good one from a bad one. Encode into 5 dimensions scored 0-10, with these concrete criteria:

| Dimension | Weight | Score 0-3 | Score 4-6 | Score 7-10 |
|-----------|--------|-----------|-----------|------------|
| Problem clarity | 25% | Vague or me-too problem | Specific problem, fuzzy audience | One sentence that nails who suffers and why |
| UX quality | 25% | Can't figure out what it does in 30s | Understandable but clunky | Clear in 10s, zero friction to try |
| AI integration | 20% | AI is cosmetic (chatbot wrapper) | AI does real work but replaceable | AI is the core differentiator, can't replicate manually |
| Polish | 15% | Broken states, misaligned UI, typos | Works but feels unfinished | Feels like a product someone shipped with pride |
| Novelty | 15% | Duplicate of existing product | Unique angle on known problem | New framing or new problem nobody solved |

Score = weighted average * 10 (0-100 final). GPT-4o prompt should include the full table above plus 2-3 example scored apps as calibration anchors. Publish the per-dimension breakdown with each listing so builders can learn from the critique.

**Sample prompt structure for GPT-4o scoring:**
```
You are scoring an AI app on 5 dimensions (0-10 each).
Rubric: [full table above]
Calibration: [2 pre-scored examples]
App URL screenshot: [image]
App description: [text]
Return JSON: {problem_clarity: N, ux_quality: N, ai_integration: N, polish: N, novelty: N, critique: "1-2 paragraph reasoning"}
```

**Error handling requirements (critical gaps from eng review):**
- GPT-4o malformed/invalid JSON response: catch parse error, set `status: scoring_failed` (new status value), log error. Do NOT leave listing in `status: pending` indefinitely. Creator should see "Scoring failed — submit a re-score request."
- Relay decrypt failure (wrong EMAIL_ENCRYPTION_KEY): catch decryption error, log with listing_id and relay_token_id, set `forwarded_at` to a sentinel error value (or add a `forward_status: failed` column), alert the founder. Do NOT silently drop the buyer inquiry.
- Relay token past `expires_at`: return HTTP 410 Gone with body "This contact link has expired." Do not forward.
- Add `scoring_failed` to listings.status enum: `status[pending|scored|scoring_failed|rejected]`.

**Performance note — feed query:**
The public feed must JOIN listings + users in a single query. Use Supabase's `.select('*, users(display_name, avatar_url)')` — do NOT fetch creator info in a loop (N+1 query: one database round-trip per listing, 20 listings = 21 queries). Default page size: 20 listings. Add Postgres index on `listings.score DESC` and `listings.category`.

## Open Questions

- How do you prevent spam submissions? V1: auto-approve all first submissions (no moderation queue — removes the founder bottleneck that would kill a weekend launch). Rate limit: max 3 submissions per account per week, enforced at DB level (count rows in submission_log for user in last 7 days before insert). If limit hit, return 429 with "You've reached your submission limit this week." Manual takedown tool available to founder for obvious spam/malware after the fact. Moderation queue is a V2 feature once volume justifies it.
- What categories make sense for V1? (Productivity, Writing, Code, Design, Research, Other)
- Should the AI score be re-run if the app updates? Sellers can request one free re-score per day, but only when they update listing content (description, screenshots, or URL). Re-score on unchanged content is not allowed. Add `score_version` (int, starts at 1) and `last_rescored_at` (timestamp) to listings. Re-score increments `score_version`. This prevents arbitrary re-rolling and limits GPT-4o non-determinism from confusing sellers.
- Dispute mechanism: let creators request a manual re-review? (V2 feature)

## Success Criteria

- 10 listings with AI scores by end of first weekend
- At least 1 buyer-seller contact initiated (measured by: relay token `forwarded_at` not null — platform logs every forward, founder can query Supabase directly)
- Post to indie hackers with link + screenshot of the scoring breakdown. Qualitative validation: at least 3 builders respond with "that score feels right/wrong and here's why." Collect in comments, not in-app.

## Distribution Plan

- Vercel for hosting (zero config, free tier)
- Resend or Postmark for email relay
- Initial distribution: post to Indie Hackers, r/SideProject, Twitter/X builder communities
- The AI score badge is linkable — "my app scored 84/100" is shareable

## Prerequisites (before coding)

**Block 1 — Rubric calibration (2-3 hours, do this first, in parallel with repo/Supabase setup):**
Evaluate 5-10 AI apps manually. Score each on all 5 dimensions using the rubric table. Select 3 as calibration anchors: one low (30-40), one mid (55-65), one high (75-85). Write out the full score + critique for each anchor — these become the few-shot examples in the GPT-4o prompt. After the eval pipeline is built, score those same 3 anchors with GPT-4o and compare. If any dimension diverges by >10 points, add another example. V1 scope: cut GitHub OAuth — email/password only. This saves ~1.5 hours and cuts a V1 auth edge case that doesn't affect the core product. GitHub OAuth is a V2 feature.
